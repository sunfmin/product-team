- When a module's issue needs a capability the kernel or platform lacks (a view's range, a read across tables), open issues for that capability now, make them block the module's issue, and keep the module's issue as written; never narrow it, and never record a derived value (a display name) to work around the gap. **When:** the issue's acceptance criteria cannot be met with what the platform offers today. (https://github.com/sunfmin/bizkernel/issues/403)
- When a failure that went red once (a test, a check of the gate) does not fail again, it gets at most two bounded attempts to reproduce it, each leaving its raw output on the issue; still not reproduced, the issue is closed with that record and "If it recurs, reopen with the raw failure output" (the lead closes it with `gh issue close <n> --comment`), or let through to a human, and it is never investigated again. **When:** a flaky failure that no attempt reproduced; one that reproduces is fixed like any other failure. (https://github.com/sunfmin/bizkernel/issues/668#issuecomment-6338325491)
- When a builder's run ended on its own background work (the gate, a suite, a build it started and never read the end of), the builder runs that work again in the foreground, or waits on it with bounded foreground checks, reads what it printed, and declares; nothing else is redone. **When:** a `build` stage failed silent or stopped while its own command was still running. (https://github.com/sunfmin/bizkernel/issues/512#issuecomment-6305900042, https://github.com/sunfmin/bizkernel/issues/532#issuecomment-6305911346, https://github.com/sunfmin/bizkernel/issues/534#issuecomment-6305916430, https://github.com/sunfmin/bizkernel/issues/543#issuecomment-6306057339, https://github.com/sunfmin/bizkernel/issues/605#issuecomment-6311186315, https://github.com/sunfmin/bizkernel/issues/606#issuecomment-6311263256, https://github.com/sunfmin/bizkernel/issues/659#issuecomment-6319945920)
- When a stage was failed as "blocked, named no blocker" because its only blocker is an issue in another repo, check that issue: closed with its fix merged → rule `build` to resume on the same branch, bump the pin to a rev that has the fix (that repo's `main` when it does), finish the issue as written, and drop nothing; still open → park the stage until it closes. **When:** the stage record names the cross-repo blocker and it is a GitHub dependency of the issue. (https://github.com/wangweixingsz/tcmsaas/issues/136#issuecomment-6374974271, https://github.com/wangweixingsz/tcmsaas/issues/155)
- When written decisions conflict, or an issue cannot be met as written, the lead picks the option rule 2 ranks first, names the decision that gives way and why, and has it amended in the same stage; only a rule 5 case goes to a human. **When:** an issue conflicts with an accepted ADR, the glossary or another written decision, as when hostvitals was ruled to read arguments through the environment-capable `KERN_PROCARGS2` buffer (#56, **buffer**) and to retain a profile's raw sample report despite the general no-report ADR (#57, **retain**). (https://github.com/sunfmin/control/issues/56#issuecomment-6406525515, https://github.com/sunfmin/control/issues/57#issuecomment-6406527660)
- When a build stage is escalated because the host failed to start its worker, resume the existing build under its current brief and acceptance criteria, preserving its unpushed commits and changes. **When:** the host fault is fixed and a worker can start, and the escalation identified no issue or repo defect. (https://github.com/sunfmin/control/issues/130#issuecomment-6429310007)
